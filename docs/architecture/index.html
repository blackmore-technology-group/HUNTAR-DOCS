Technical overview

Technology & Architecture

A public-safe view of the layers that make HuntAR work without publishing proprietary model internals or security-sensitive material.

System layers

HuntAR UI & field workflows → species/terrain intelligence → BSIE spatial world → ARKit + Metal + GNSS/motion → local/offline data → optional connected services

HuntAR application layer

Owns the field interface, species selection, Hunt Area workflows, waypoints, routes, offline mapping and hunting-specific presentation.

Blackmore Spatial Intelligence Engine (BSIE)

Provides the spatial foundation used for pose, world coordinates, geometry, semantic/spatial context, persistent world state and terrain-aware rendering. The current iOS build integrates BSIE 2.3 components.

Apple spatial stack

The iOS application uses ARKit for camera/spatial tracking and Metal for native GPU rendering, together with Core Location, motion sensors and platform security APIs.

NIKI mobile runtime

HuntAR includes a bound mobile NIKI runtime within the approved application architecture. Public documentation intentionally does not expose private model weights, keys or proprietary internal decision logic.

Offline data layer

Hunt Areas, map context and local-first field records are designed to support operation without continuous cellular connectivity. Connected services can be used where configured.

ENTITY integration

The native iOS client includes optional ENTITY integration for governed identity, provenance and data-rights workflows. A valid principal binding and configured endpoint are required before ENTITY event capture/transmission. Provenance envelopes can exclude raw application content where explicitly marked.

Security boundaries

  • Configured non-local ENTITY endpoints require HTTPS.
  • Platform security APIs can provide hardware-backed device provenance where available.
  • Private keys, production credentials and sensitive bindings are not public documentation artifacts.
  • Local/offline operation and connected synchronization are separate concerns.

Evidence boundary

Documentation describes architecture and user-visible behavior. It does not claim that every terrain score is ground truth or that host testing replaces physical field validation. Real-world spatial quality depends on the device, sensors, environment, installed data and specific build.
